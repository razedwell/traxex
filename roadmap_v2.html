architecture deep-dive

Traxex is a microservices chat backend. Four services own distinct slices of the domain and communicate two ways: synchronously over gRPC (request/response, when the caller needs an answer now) and asynchronously over Kafka (fire-and-forget events, when other parts of the system should react but the caller shouldn't wait). PostgreSQL is the source of truth; Redis is the low-latency coordination layer; OpenTelemetry threads a trace through the whole thing.

Why microservices here (and the honest trade-off)

For a learning/interview project the real reason is to practice the hard parts of distributed systems: service boundaries, inter-service contracts (protobuf), eventual consistency, distributed tracing, and independent failure. In production you'd only split a monolith when you need independent deployment, independent scaling, or team autonomy. A senior answer names the costs too: network calls can fail and add latency, you now need distributed tracing to debug, data lives in multiple stores so you lose cross-service transactions, and "eventual consistency" becomes your problem. The boundaries here are drawn along bounded contexts: identity (auth), conversation (messaging), liveness (presence), and side-effects (notification).

◆ mental model — sync vs async

gRPC when you need the answer; Kafka when you don't

"Is this token valid?" must be answered before the request proceeds ⇒ gRPC (blocking, strongly typed, one caller → one callee). "A message was sent" is a fact others may care about (notify, update presence, index for search) ⇒ Kafka (non-blocking, one producer → N independent consumers, buffered, replayable).

◆ mental model — the two data planes

Postgres = truth, Redis = speed

Postgres is durable, transactional, queryable — it's where a message legally exists. Redis is in-memory — sessions, rate-limit counters, presence, pub/sub fan-out. If Redis is wiped you lose convenience (users re-login); if Postgres is wiped you lose data. Design so Redis is always reconstructable from Postgres or re-login.

The lifecycle of one "send message" request

Trace this end-to-end — it touches every technology in the stack and is the single best thing to be able to whiteboard in an interview:

  1. Client sends POST /messages to the gateway with a bearer JWT.
  2. Gateway middleware calls auth ValidateToken over gRPC → auth checks the session in Redis (fast path, no Postgres hit) and returns the user ID.
  3. Gateway checks a Redis rate-limit counter, then calls messaging SendMessage over gRPC.
  4. messaging INSERTs the row into Postgres (this is the durable commit), then produces a message.sent event to Kafka.
  5. The gRPC call returns success to the client. The work isn't done, but the client is unblocked.
  6. presence and notification independently consume message.sent: presence pushes to connected WebSocket clients via its hub (and Redis pub/sub to reach clients on other instances); notification enqueues a push via a worker pool, retrying with backoff and dead-lettering on repeated failure.
  7. Throughout, one trace_id (propagated in gRPC metadata and Kafka headers) ties every span and log line together in Grafana/Tempo + Kibana.

cross-cutting mental models

Five ideas recur in every phase. Internalize these once and the rest of the roadmap becomes pattern-matching.

◆ layered architecture

handler → service → repository → db. Handlers translate transport (gRPC/HTTP) to/from domain calls. Service holds business rules and knows nothing about gRPC or SQL. Repository hides the datastore behind an interface. Dependencies point down; the service depends on a repository interface it declares, and main.go wires the concrete impl in.

◆ context propagation

context.Context is the first arg of nearly every function. It carries deadlines/cancellation (client hangs up ⇒ DB query is aborted) and request-scoped values (trace span). Never store a context in a struct; always pass it explicitly down the call chain.

◆ typed errors, mapped at the edge

Deep code returns *traxerr.Traxerr with a semantic Code. Only the outermost handler translates that code to a gRPC status or HTTP status. Business logic never imports net/http or grpc/codes.

◆ at-least-once + idempotency

Distributed messaging delivers events at least once — duplicates happen (redelivery after a crash before commit). So consumers must be idempotent: processing the same event twice has the same effect as once (dedupe by event ID / upsert). This pairing shows up in Phases 3 & 5.

◆ dependency injection, the Go way

No framework. A constructor takes its dependencies as parameters (NewAuthService(repo UserRepository, rdb *redis.Client) *AuthService) and main.go is the single composition root that builds the object graph bottom-up: config → pools/clients → repositories → services → handlers → servers. This makes every layer trivially testable with mocks.

Theory — what these foundations actually are

Go modules & the single-module monorepo

A module is the unit of versioning and dependency in Go, declared by go.mod with a module path (github.com/razedwell/traxex). Every import inside the repo is that path + the folder. You chose a single module for the whole monorepo — one go.mod, one go.sum, one dependency set shared by all services.

▲ single module (your choice)

One dependency graph, trivial cross-package imports (shared/ → services/), one go build ./.... Downside: all services share one version of every dep; you can't release them independently. Correct for this project.

△ multi-module (not now)

Each service its own go.mod + go.work workspace to stitch them. Enables independent dependency versions and releases, at the cost of significant tooling complexity. This is a real interview discussion, not a Phase-1 need.

⚙ under the hood — the internal/ rule

Go enforces one visibility rule via the filesystem: a package under .../internal/ can only be imported by code rooted at the parent of that internal/ dir. So services/auth/internal/service is importable by services/auth/... but not by services/messaging/.... This is the compiler guaranteeing your service boundaries — no accidental coupling between services. shared/ has no internal/, so it's intentionally importable by all.

Configuration & the 12-factor precedence chain

The 12-factor rule: config lives in the environment, not in code, so the same binary runs in dev/staging/prod by changing env vars only. Viper implements a precedence chain — later sources override earlier ones. Your loader is: code defaults → config.yaml → .env → real env vars.

lowest priority ─────────────────────────────────────▶ highest priority SetDefault() ▶ config.yaml ▶ .env file ▶ OS env (APP_*, POSTGRES_*) hard-coded committed gitignored injected by docker/k8s sane dev values dev baseline local secrets prod secrets / overrides
Why the split between config.yaml and .env: the YAML is human-readable structured config safe to commit (non-secret dev defaults); the .env holds secrets and machine-specific values and is gitignored. In production there's no file at all — the orchestrator injects env vars, which sit at the top of the precedence chain and win.
⚙ under the hood — why you load .env with gotenv, not viper

Your code comment nails a subtle bug: if you ReadInConfig a .env as a second config file, viper flattens dotted keys and can clobber nested YAML (e.g. wipe database.password). Instead you gotenv.Load() the .env into the process environment, then BindEnv/AutomaticEnv let those env vars override at read time — precedence preserved, nesting intact.

Error handling in Go — the model interviewers test

Go has no exceptions. Errors are ordinary values that you return and check. Three things you must be able to explain:

  • Wrapping & the chain. fmt.Errorf("...: %w", err) wraps err so the original is retrievable. This builds a chain: handler err → service err → repo err → pgx err. Never %v when you want to preserve the chain — use %w.
  • errors.Is vs errors.As. Is(err, target) walks the chain looking for a specific sentinel value (e.g. pgx.ErrNoRows). As(err, &target) walks the chain looking for a specific type and, if found, assigns it — that's how traxerr.IsCode pulls your *Traxerr back out of a wrapped chain.
  • Sentinel vs typed errors. A sentinel is a package-level var ErrX = errors.New(...) compared with Is. A typed error is a struct carrying data (your Traxerr with a Code, Message, Details) matched with As. Typed errors are richer — they survive to the edge where you map Code → gRPC status.
panic vs error. Return an error for anything expected (bad input, not found, network blip). panic only for programmer bugs / truly unrecoverable state, and recover at goroutine boundaries (e.g. a gRPC interceptor) so one bad request can't crash the process.

Connection pooling — pgx & the pool you almost never see

Opening a TCP connection + TLS + Postgres auth handshake costs milliseconds — far too expensive per query. A connection pool keeps a set of live connections and hands them out. pgxpool (built on the puddle generic pool) manages this: on Acquire you get an idle conn or a new one is opened (up to MaxConns); on release it returns to the pool. QueryRow/Exec on the pool acquire-and-release automatically for a single statement.

⚙ under the hood — pool sizing & the killer footgun

Postgres handles concurrency with one OS process per connection — connections are heavy server-side. Total connections across all service instances must stay under the server's max_connections (default 100). With 4 services × 3 replicas × pool of 10 = 120 > 100 ⇒ "too many clients" errors. Right-size pools; in real infra put a PgBouncer in front. A common formula for CPU-bound query workloads is pool ≈ ((core_count × 2) + effective_spindle_count).

The classic footgun: acquiring a connection and forgetting to release it (e.g. iterating rows without rows.Close(), or holding a tx). Leaked connections drain the pool until every request blocks on Acquire. Always pass a context with a deadline so a stuck acquire fails fast instead of hanging forever.

Structured logging with zap

"Structured" means each log line is machine-parseable key/value data (JSON), not a formatted sentence. logger.Info("user registered", zap.String("user_id", id)) emits a JSON object — greppable and indexable in Kibana. zap is fast because the hot path (its Core) avoids reflection and allocations; zap.String etc. build strongly-typed fields directly.

  • Production vs Development config. Your InitLogger picks NewProductionConfig() (JSON, info+, sampling) for format:"json" and NewDevelopmentConfig() (console, colored, human) otherwise — exactly right.
  • Levels gate volume: debug (dev firehose) → info (normal events) → warn (recoverable) → error (needs attention) → fatal (logs then os.Exit(1)). Set via config, not code.
  • Sync() flushes buffered logs — always defer logger.Sync() in main.

Kafka & Docker Compose — just enough for Phase 1 (deep dive in Phase 3)

For now: a Producer wraps a kafka.Writer (knows the brokers + a topic, load-balances across partitions); a Consumer wraps a kafka.Reader (a broker set, topic, and GroupID). The full model of partitions, offsets, consumer groups, and delivery semantics is Phase 3. The one Compose subtlety worth understanding now is the dual Kafka listener.

⚙ under the hood — why Kafka needs two listeners in Compose

Kafka clients first hit a bootstrap address, then the broker replies with the advertised address to actually connect to. Inside the Docker network, containers reach the broker as kafka:9092; from your host (where your Go service runs during dev) that hostname doesn't resolve — you need localhost:29092. So the broker advertises two listeners (PLAINTEXT://kafka:9092 for in-network, PLAINTEXT_HOST://localhost:29092 for the host). Your config.yaml correctly points brokers at 127.0.0.1:29092. Get this wrong and you'll see the maddening "connects, then times out on produce" symptom.

Theory — everything the steps assume

gRPC, from the wire up

gRPC is an RPC framework: you call a method on a local stub, it serializes the args with Protocol Buffers, ships them over HTTP/2 to the server, which deserializes, runs your handler, and sends the reply back the same way. You define the contract once in a .proto file; protoc generates both the client stub and the server interface.

⚙ under the hood — why HTTP/2 matters

HTTP/1.1 is one request per connection at a time (head-of-line blocking); to parallelize you open many connections. HTTP/2 introduces: (1) multiplexing — many concurrent "streams" over a single TCP connection, each stream a request/response; (2) binary framing — messages are binary frames (HEADERS, DATA), not text; (3) header compression (HPACK); (4) full-duplex streams — both sides can send frames anytime. gRPC maps each RPC to one HTTP/2 stream, which is exactly why gRPC gets cheap streaming and low overhead. The method is a path (/auth.v1.AuthService/Login); the message is the DATA frame body.

Interceptors = middleware

An interceptor wraps every RPC — the gRPC equivalent of HTTP middleware. Protocol Buffers — the contract & wire format

A .proto defines messages (typed records) and services (RPC methods). The magic is the field number — the integer after each field. On the wire, protobuf encodes field_number << 3 | wire_type as a tag, then the value. Field names are never sent; only numbers. That's why protobuf is compact and why the compatibility rules are what they are.

⚙ under the hood — wire types & compatibility

There are a handful of wire types: 0 varint (int32/64, bool, enum), 1 64-bit, 2 length-delimited (string, bytes, embedded messages, packed repeated), 5 32-bit. Varints encode small numbers in fewer bytes (7 bits per byte + continuation bit). Compatibility rules that follow directly:

  • Never reuse or change a field number — old clients would misread new data. Reserve removed numbers with reserved.
  • Adding a field is safe — old readers skip unknown tags; new readers get the zero value from old writers.
  • proto3 has no "required" and no field presence for scalars by default — an unset int32 and an explicit 0 look identical on the wire (the field is simply omitted). Use optional or wrapper types when you must distinguish "unset" from "zero."
Timestamps & well-known types: use google.protobuf.Timestamp for created_at (maps to Go *timestamppb.Timestamp, convert with timestamppb.New(t) / .AsTime()). Version your package: package auth.v1; so you can ship a v2 later without breaking v1 callers.

JWT — structure, signing, and the stateful/stateless decision

A JWT is three base64url segments joined by dots: header.payload.signature.

header {"alg":"HS256","typ":"JWT"} // which signing algorithm payload {"sub":"user-uuid","exp":1750000000,...} // "claims" — NOT encrypted, only signed signature HMAC_SHA256(base64(header)+"."+base64(payload), secret)

The signature proves the token was issued by someone holding the secret and hasn't been tampered with. Crucially the payload is signed, not encrypted — anyone can base64-decode and read the claims, so never put secrets in them. Standard claims: sub (subject/user id), iat (issued-at), exp (expiry), nbf (not-before), jti (token id).

HS256 (symmetric)

One shared secret signs and verifies. Simple; fine when the same trust domain issues and validates. Anyone who can verify can also forge.

RS256 / ES256 (asymmetric)

Private key signs, public key verifies. Other services verify without being able to mint tokens. Preferred once multiple independent verifiers exist. Name this trade-off in interviews.

⚙ under the hood — access vs refresh, and why you still touch Redis

Pure stateless JWT has a fatal flaw: you can't revoke a token before it expires (logout, "sign out all devices," stolen token). The standard fix is two tokens: a short-lived access token (minutes) carried on every request, and a long-lived refresh token (days) exchanged for a new access token. You store the refresh/session state in Redis keyed by user/session with a TTL. Logout deletes the session; a stolen refresh token is revocable. So ValidateToken verifies the access JWT signature+expiry (cheap, stateless) but session lifecycle lives in Redis (revocable). That hybrid — stateless access + stateful refresh — is the pragmatic senior answer.

Refresh-token rotation: each refresh issues a new refresh token and invalidates the old one; if an old one is ever reused, you've detected theft and can nuke the whole session family.

bcrypt — why you never SHA-256 a password

Passwords must be stored as a slow, salted, adaptive hash. bcrypt is exactly that.

  • Salt — a random per-password value mixed in, stored inside the bcrypt output. Defeats rainbow tables and makes two identical passwords hash differently. bcrypt generates & embeds the salt for you.
  • Cost / work factor — bcrypt runs 2^cost rounds. Higher cost = slower = harder to brute force. Use cost 12 in prod, 4 in tests (so tests stay fast). It's "adaptive": bump cost as hardware improves.
  • Why not SHA-256? SHA-256 is fast — an attacker with a GPU tries billions/sec. bcrypt is deliberately slow and memory-touching. (Argon2id is the modern alternative; bcrypt is the battle-tested default and what golang.org/x/crypto/bcrypt gives you.)
  • Verify with CompareHashAndPassword, which is constant-time to avoid timing attacks — never compare hashes with ==.

Multi-stage Docker builds

A Go binary is statically linkable — the final image needs only the binary, not the Go toolchain. A multi-stage build compiles in a fat golang stage, then copies just the binary into a tiny distroless/scratch final stage (~10–20 MB vs ~1 GB).

⚙ under the hood — CGO, static linking, and why scratch works

Set CGO_ENABLED=0 so the binary has no libc dependency (fully static). Then FROM scratch or gcr.io/distroless/static works because there's nothing to link at runtime. distroless is preferred over scratch when you need CA certificates (for outbound TLS) and timezone data, which it bundles. Smaller image = faster pulls, smaller attack surface (no shell, no package manager).

type PostgresUserRepo struct{ pool *pgxpool.Pool }

func NewPostgresUserRepo(pool *pgxpool.Pool) *PostgresUserRepo { return &PostgresUserRepo{pool: pool} }

func (r *PostgresUserRepo) Create(ctx context.Context, u domain.User) (domain.User, error) {
    const q = `INSERT INTO users (email, password_hash)
               VALUES ($1, $2) RETURNING id, created_at`
    err := r.pool.QueryRow(ctx, q, u.Email, u.PasswordHash).Scan(&u.ID, &u.CreatedAt)
    if err != nil {
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && pgErr.Code == "23505" { // unique_violation
            return domain.User{}, domain.ErrEmailTaken()
        }
        return domain.User{}, fmt.Errorf("create user: %w", err)
    }
    return u, nil
}

func (r *PostgresUserRepo) GetByEmail(ctx context.Context, email string) (domain.User, error) {
    const q = `SELECT id, email, password_hash, created_at FROM users WHERE email = $1`
    var u domain.User
    err := r.pool.QueryRow(ctx, q, email).Scan(&u.ID, &u.Email, &u.PasswordHash, &u.CreatedAt)
    if errors.Is(err, pgx.ErrNoRows) {
        return domain.User{}, domain.ErrUserNotFound()
    }
    if err != nil {
        return domain.User{}, fmt.Errorf("get user by email: %w", err)
    }
    return u, nil
}
⚙ under the hood — parameterized queries stop SQL injection

$1, $2 placeholders send the query and the values separately — pgx uses Postgres's extended query protocol (Parse/Bind), so user input is never string-concatenated into SQL. This is why you never build queries with fmt.Sprintf. The RETURNING clause gets the DB-generated id/timestamp back in the same round-trip.

Postgres error code 23505 = unique_violation. Mapping it to a domain error here keeps the "email taken" concept out of the service layer while still catching the race the UNIQUE constraint guards.

import (
    "github.com/golang-jwt/jwt/v5"
    "github.com/google/uuid"
    "golang.org/x/crypto/bcrypt"
)

func (a *AuthService) Register(ctx context.Context, email, password string) (domain.User, error) {
    hash, err := bcrypt.GenerateFromPassword([]byte(password), a.bcryptCost)
    if err != nil {
        return domain.User{}, traxerr.Wrap(traxerr.CodeInternal, "hash password", err)
    }
    return a.repo.Create(ctx, domain.User{Email: email, PasswordHash: string(hash)})
    // repo maps duplicate-email → domain.ErrEmailTaken()
}

func (a *AuthService) Login(ctx context.Context, email, password string) (access, refresh string, expiresIn int64, err error) {
    u, err := a.repo.GetByEmail(ctx, email)
    if err != nil {
        return "", "", 0, domain.ErrInvalidCredentials() // do NOT leak "user not found"
    }
    if err := bcrypt.CompareHashAndPassword([]byte(u.PasswordHash), []byte(password)); err != nil {
        return "", "", 0, domain.ErrInvalidCredentials()
    }
    return a.issueTokens(ctx, u.ID)
}

func (a *AuthService) issueTokens(ctx context.Context, userID string) (string, string, int64, error) {
    now := time.Now()
    claims := jwt.MapClaims{
        "sub": userID,
        "iat": now.Unix(),
        "exp": now.Add(a.accessTTL).Unix(),
    }
    access, err := jwt.NewWithClaims(jwt.SigningMethodHS256, claims).SignedString(a.jwtSecret)
    if err != nil {
        return "", "", 0, traxerr.Wrap(traxerr.CodeInternal, "sign token", err)
    }
    refresh := uuid.NewString() // opaque; the DB of record is Redis
    sess := domain.Session{UserID: userID, RefreshToken: refresh, CreatedAt: now, ExpiresAt: now.Add(a.refreshTTL)}
    if err := a.sessions.Save(ctx, sess, a.refreshTTL); err != nil {
        return "", "", 0, traxerr.Wrap(traxerr.CodeInternal, "save session", err)
    }
    return access, refresh, int64(a.accessTTL.Seconds()), nil
}

func (a *AuthService) ValidateToken(ctx context.Context, access string) (string, error) {
    tok, err := jwt.Parse(access, func(t *jwt.Token) (any, error) {
        if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok { // reject alg confusion
            return nil, domain.ErrTokenInvalid()
        }
        return a.jwtSecret, nil
    })
    if err != nil || !tok.Valid {
        return "", domain.ErrTokenInvalid()
    }
    claims, _ := tok.Claims.(jwt.MapClaims)
    sub, _ := claims["sub"].(string)
    if sub == "" {
        return "", domain.ErrTokenInvalid()
    }
    return sub, nil // NOTE: no Redis hit — stateless verification, fast
}

func (a *AuthService) Refresh(ctx context.Context, refresh string) (string, string, int64, error) {
    sess, err := a.sessions.Get(ctx, refresh)
    if err != nil {
        return "", "", 0, domain.ErrTokenInvalid()
    }
    _ = a.sessions.Delete(ctx, refresh)      // rotation: old refresh dies now
    return a.issueTokens(ctx, sess.UserID)   // mint a fresh pair
}

func (a *AuthService) Logout(ctx context.Context, refresh string) error {
    return a.sessions.Delete(ctx, refresh)   // revoke — the whole point of stateful refresh
}
⚙ under the hood — the "alg=none" / algorithm-confusion attack

A classic JWT vuln: a library that trusts the token's alg header can be tricked. If you use RS256 and the attacker sets alg:HS256, a naive verifier might HMAC-verify using the public key (which the attacker knows) as the secret. The keyfunc above defends by asserting the method type is what you expect (*SigningMethodHMAC) before returning the key. Always pin the algorithm.

    if errors.As(err, &te) {
        return status.Error(traxerr.GRPCCode(te.Code), te.Message)
    }
    return status.Error(codes.Internal, "internal error") // never leak internals
}

Interview drills

Walk me through what happens when a JWT is validated. Why can you skip the database?
The access token is header.payload.signature. Validation recomputes the HMAC (HS256) over header.payload with the server secret and compares it to the signature — if it matches, the token wasn't forged or tampered with. Then check exp. Because the signature is the proof of authenticity and the claims (sub) are inside the signed payload, no datastore lookup is needed — it's stateless, so it's fast and scales horizontally. The trade-off: you can't revoke an unexpired access token, which is why access tokens are short-lived (15 min) and revocation happens at the refresh layer, which is stateful in Redis.
Why store sessions in Redis at all if JWTs are stateless?
To get revocation and rotation. Pure stateless JWT can't do logout, "log out everywhere," or invalidate a stolen token before expiry. The hybrid: short-lived stateless access tokens (cheap validation, no Redis hit on the hot path) + long-lived opaque refresh tokens whose state lives in Redis (revocable, rotatable). Logout deletes the Redis session; refresh rotation detects token theft by invalidating reused refresh tokens.
Two requests register the same email simultaneously. What prevents duplicates?
A UNIQUE constraint on users.email. A "SELECT to check, then INSERT" is a TOCTOU race — both requests can pass the check before either inserts. The DB constraint is the real guarantee: the second INSERT fails with Postgres error 23505, which the repository maps to ErrEmailTaken. Belt-and-suspenders: you can pre-check for a friendly message, but the constraint is what makes it correct.
Why bcrypt and not SHA-256 with a salt?
Password hashes must be slow. SHA-256 is designed to be fast — a GPU tries billions/sec, so even salted hashes fall to brute force. bcrypt has a tunable cost factor (2^cost rounds) so you make each guess expensive and raise the cost as hardware improves. It also generates and embeds a per-password salt. Argon2id is the modern memory-hard alternative; bcrypt is the safe, ubiquitous default.
You expose the same logic over gRPC and REST. How do you avoid duplicating it?
All business logic lives in the service layer, which depends only on interfaces (repository, session store) and knows nothing about transport. The gRPC handler and the HTTP handler are thin adapters: decode the transport-specific request, call the identical service method, encode the response, and map the typed traxerr.Code to a gRPC status or HTTP status at that single edge. Handlers are ~40 lines of translation each; there's exactly one implementation of the actual behavior.
What's the "algorithm confusion" JWT attack and how do you defend?
If a verifier blindly trusts the token's alg header, an attacker can downgrade an RS256 setup to HS256 and sign with the public key (which they know) as the HMAC secret — the verifier would "verify" it successfully. Defense: pin the expected algorithm in the keyfunc (assert t.Method is the type you expect) and never let the token dictate the verification method. Also reject alg:none.

Theory — Kafka from first principles

The core abstraction: a partitioned, replicated, append-only log

Kafka is not a queue in the RabbitMQ sense — it's a distributed commit log. Producers append records to the end of a log; consumers read forward from a position they track. Records aren't deleted when read — they live until a retention policy expires them. That single design decision is why Kafka supports replay, multiple independent consumers, and event sourcing.

TermWhat it is
BrokerOne Kafka server. A cluster is several brokers. (Your Compose runs one broker + zookeeper.)
TopicA named log, e.g. message.sent. Purely a logical category.
PartitionThe unit of parallelism & ordering. A topic is split into N partitions; each is an independent ordered log with its own offsets. Ordering is guaranteed within a partition, never across partitions.
OffsetA monotonically increasing integer id of a record within a partition. A consumer's position = the next offset to read.
Recordkey + value + headers + timestamp. The key determines the partition.
SegmentA partition's on-disk log is chunked into segment files; retention/compaction operate per segment.
topic "message.sent", 3 partitions: P0: [0][1][2][3][4] ← append key hash % 3 == 0 P1: [0][1][2] ← append key hash % 3 == 1 P2: [0][1][2][3][4][5][6] ← append key hash % 3 == 2 ▲consumer-A offset=3 ▲producer writes to tail

Keys, partitioning & ordering — the decision that bites people

The producer picks a partition by hash(key) % numPartitions (or round-robin if key is nil — your LeastBytes balancer is a variant for null keys). All records with the same key go to the same partition, so they stay ordered. This is the lever you pull for correctness: key message.sent events by room_id so all messages in a conversation are ordered relative to each other, even though the global topic has no total order.

Consequences to be able to state: (1) more partitions = more parallelism but less ordering scope. (2) You can add partitions later, but it changes hash(key)%N, so historical key→partition mapping breaks — pick partition count deliberately. (3) A single partition is only consumed by one consumer within a group, so partition count caps a group's parallelism.

Replication, leaders, ISR, and acks

Each partition has a leader replica and (in prod) follower replicas on other brokers. Producers/consumers talk to the leader; followers replicate. The ISR (in-sync replicas) is the set of replicas caught up to the leader. Durability is governed by the producer's acks:

acksMeaningGuarantee / risk
0Fire and forget; don't waitFastest; can silently lose records
1Wait for leader writeLost if leader dies before followers replicate
all (-1)Wait for all ISRStrongest durability; with min.insync.replicas≥2, survives a broker loss. Use this for anything that matters.

Consumer groups & rebalancing

A consumer group is a set of consumers sharing a group.id that cooperatively divide a topic's partitions — each partition is assigned to exactly one consumer in the group. That's horizontal scaling: add consumers (up to the partition count) to go faster. Different groups are independent — notification-service and presence-service each read the whole topic at their own pace with their own offsets. When a consumer joins/leaves/dies, the group rebalances — partitions are reassigned.

⚙ under the hood — offsets are stored in Kafka itself

A group's committed offsets live in an internal compacted topic __consumer_offsets, keyed by (group, topic, partition). "Committing an offset" means recording "this group has processed up to here." On rebalance/restart, a consumer resumes from the committed offset. This is why when you commit (before vs after processing) decides your delivery semantics — the crux of the next section.

Delivery semantics — the senior-defining topic

at-most-once

Commit offset before processing. Crash mid-process ⇒ record skipped on restart. No duplicates, possible loss. Rarely acceptable.

at-least-once

Commit after successful processing. Crash after processing but before commit ⇒ record reprocessed. No loss, possible duplicates. The default you build.

exactly-once

Idempotent producer + transactions (consume-process-produce atomically), or at-least-once + idempotent consumer. Real but costly.

The pragmatic pattern (what you'll implement): at-least-once delivery + idempotent consumers. Accept that duplicates happen; make processing safe to repeat (dedupe by event id, or use upserts). This gives effectively-once results without the cost of Kafka transactions. Say exactly these words in an interview.

The dual-write problem & the Outbox pattern

Your SendMessage must do two things: write the message to Postgres and publish message.sent to Kafka. These are two separate systems — you cannot wrap both in one transaction. This is the dual-write problem: whatever order you choose, a crash between the two leaves them inconsistent.

naive (has a failure window): INSERT message ──✓──▶ produce message.sent ──✗ crash──▶ DB has it, Kafka doesn't produce first ──✓──▶ INSERT message ──✗ crash──▶ Kafka has it, DB doesn't (worse)

The correct order for now is DB-first, then publish: if the publish fails you can log/retry, and readers can still read the message from Postgres (eventual delivery of the event). But the airtight solution is the Transactional Outbox:

⚙ under the hood — the Outbox pattern

In the same DB transaction as the message insert, also insert a row into an outbox table describing the event. The transaction makes both writes atomic — they commit together or not at all. A separate relay process (or Debezium CDC tailing the WAL) reads unpublished outbox rows and publishes them to Kafka, marking them sent. Because the relay is at-least-once, consumers still need idempotency — but you've eliminated the "DB and Kafka disagree" window entirely.

Roadmap stance: implement DB-first-then-publish in Phase 3 (simple, correct-enough for a chat app; the message exists even if the event is delayed). Understand and be ready to whiteboard the outbox — it's a top-tier interview answer for "how do you avoid losing events?"

gRPC server streaming (for GetHistory)

Fetching a long conversation as one giant response is wasteful and blocks memory. Server streaming lets the client send one request and the server push a stream of Message responses, each over the same HTTP/2 stream, ended by returning from the handler. The client ranges over the stream until io.EOF. It's back-pressured by HTTP/2 flow control, and cancellable via context.

Pagination: keyset (cursor) beats OFFSET

LIMIT n OFFSET m is simple but degrades: the DB must scan and discard m rows every page — page 10,000 reads 200,000 rows. It's also unstable: new inserts shift rows and you get duplicates/gaps. Keyset (cursor) pagination instead says "give me the next N rows after this (created_at, id)". With the right index it's O(N) regardless of how deep you page, and stable under concurrent inserts.

sql keyset vs offset
-- SLOW, unstable (offset):
SELECT * FROM messages WHERE room_id=$1 ORDER BY created_at DESC LIMIT 50 OFFSET 5000;

-- FAST, stable (keyset): cursor = last row's (created_at,id) from previous page
SELECT * FROM messages
WHERE room_id = $1 AND (created_at, id) < ($2, $3)   -- row-value comparison
ORDER BY created_at DESC, id DESC
LIMIT 50;

Postgres indexing — why the composite index is not optional

A B-tree index is a sorted structure that turns a full-table scan into a logarithmic lookup. For WHERE room_id=$1 ORDER BY created_at DESC you want a composite index (room_id, created_at DESC): Postgres seeks to the room_id group and reads rows already in created_at order — no separate sort step. Column order matters: equality columns first, then the range/sort column.

⚙ under the hood — read EXPLAIN like a senior

Run EXPLAIN (ANALYZE, BUFFERS) SELECT …. You want to see Index Scan using idx_messages_room_created, not Seq Scan followed by Sort. A Seq Scan on a hot query = a missing/unused index. Index Only Scan is even better (all needed columns are in the index, no heap fetch). The rows estimate vs actual rows gap tells you if stats are stale (ANALYZE).

func (r *PostgresMessageRepo) GetHistory(ctx context.Context, roomID string, limit int,
    beforeAt time.Time, beforeID string) ([]domain.Message, error) {

    // first page: beforeID empty -> use a sentinel far-future cursor
    const q = `
        SELECT id, room_id, sender_id, content, created_at
        FROM messages
        WHERE room_id = $1
          AND ($2 = '' OR (created_at, id) < ($3, $4))
        ORDER BY created_at DESC, id DESC
        LIMIT $5`

    if err != nil {

        out = append(out, m)
    }

}

Interview drills

How does Kafka guarantee ordering, and what's the catch?
Ordering is guaranteed only within a partition. The producer routes a record by hash(key) % partitions, so all records with the same key land in the same partition and keep their append order. There is no total order across partitions. So you get ordering where you need it by choosing the key deliberately — here, room_id, so each conversation is ordered. The catch: this couples your ordering scope to your partitioning, and changing partition count later remaps keys.
You must write to Postgres and publish to Kafka. How do you avoid inconsistency?
That's the dual-write problem — two systems, no shared transaction. Naive ordering leaves a crash window. Two answers: (1) Pragmatic — DB first (source of truth), then publish; a failed publish doesn't lose the message (it's in Postgres) and can be retried/reconciled, and consumers are idempotent anyway. (2) Airtight — the Transactional Outbox: insert the event into an outbox table in the same DB transaction as the message, then a relay/CDC process publishes outbox rows to Kafka at-least-once. The outbox eliminates the divergence window; consumers still dedupe by event id.
Difference between at-least-once and exactly-once? Which do you build and why?
At-least-once commits offsets after processing, so a crash before commit reprocesses — no loss, possible duplicates. Exactly-once needs Kafka's idempotent producer + transactions (atomic consume-process-produce) or, more commonly, at-least-once plus an idempotent consumer. I build at-least-once + idempotent consumers (dedupe by event id / upsert), which yields effectively-once results without the throughput and complexity cost of Kafka transactions.
Why is OFFSET pagination bad at scale? What do you use instead?
OFFSET m makes the DB scan and throw away m rows every page, so deep pages get linearly slower, and concurrent inserts shift rows causing duplicates/gaps. Keyset (cursor) pagination filters WHERE (created_at, id) < (last_seen) ordered by the same key, backed by a composite index — it's O(page size) at any depth and stable under inserts. The cursor is the last row's sort key from the previous page.
A consumer group has 3 consumers and the topic has 2 partitions. What happens?
Each partition is owned by exactly one consumer in the group, so 2 consumers get one partition each and the 3rd sits idle. Parallelism within a group is capped at the partition count. To scale past 2, you'd add partitions (which triggers a rebalance and remaps keys). Different groups are independent and each read all partitions.
What does acks=all buy you, and what else must be set?
acks=all means the producer waits until all in-sync replicas have the record before acking — it survives a broker failure. But it only helps if there are replicas: set min.insync.replicas ≥ 2 (with RF ≥ 3) so a write is rejected rather than silently under-replicated when replicas fall behind. Pair with the idempotent producer to avoid duplicates from retries. acks=1 risks loss if the leader dies pre-replication; acks=0 can lose data freely.

Theory — Go concurrency, deeply

Goroutines & the scheduler (the GMP model)

A goroutine is a function scheduled by the Go runtime, not the OS. It starts with a tiny (~2 KB) growable stack, so you can run hundreds of thousands. The runtime multiplexes many goroutines onto few OS threads — M:N scheduling — via three entities:

LetterIsRole
GGoroutineThe work: a stack + program counter + state.
MMachine (OS thread)What actually runs code on a CPU.
PProcessor (logical)A scheduling context holding a run-queue of Gs. Count = GOMAXPROCS (default = #CPUs). An M must hold a P to run Go code.
⚙ under the hood — why goroutines beat threads & how blocking works

Each P has a local run-queue of runnable goroutines (plus a global queue). An M grabs a P, runs Gs from its queue, and when its queue empties it work-steals from other Ps. Context switching between goroutines is a cheap userspace stack swap — no kernel trap — which is why goroutines are orders of magnitude lighter than threads.

The killer feature is blocking I/O: when a goroutine makes a blocking syscall (network read), the runtime detaches the M+G and hands the P to another M so other goroutines keep running. Network I/O specifically goes through the netpoller (epoll/kqueue): the goroutine is parked until the fd is ready, freeing the thread entirely. Since Go 1.14 the scheduler is asynchronously preemptible (signal-based), so a tight CPU loop can't starve others. This is precisely why a Go server can hold 100k idle WebSocket connections cheaply — each is a parked goroutine, not a thread.

Channels — typed pipes with built-in synchronization

A channel is a typed conduit; ch <- v sends, v := <-ch receives. Beyond passing data, a channel synchronizes goroutines. The semantics you must know cold:

  • Buffered = async up to N. Decouples producer/consumer speed; the buffer is a bounded queue. Use for work distribution + backpressure.
  • Closing is a broadcast "no more values." Only the sender closes, never the receiver, and never twice. A closed channel is how you fan-out a "stop" signal to many goroutines.
  • Nil channels are useful: a nil channel blocks forever, so setting a channel to nil in a select disables that case — a real idiom for dynamically turning branches off.

select — waiting on multiple channels

select blocks until one of its cases can proceed; if several are ready it picks one at random (prevents starvation). Patterns:

The Go memory model & data races

A data race is two goroutines accessing the same memory concurrently, at least one writing, with no synchronization. It's undefined behavior — torn reads, stale values, corruption — and often invisible until production load. The memory model defines happens-before: without a synchronizing event (channel op, mutex, sync/atomic), one goroutine's writes are not guaranteed visible to another. You make writes visible by synchronizing.

⚙ under the hood — the race detector

go test -race / go run -race instruments memory accesses and uses a happens-before algorithm to detect races that actually occur at runtime (it won't find races on code paths you don't exercise). It's the single most valuable tool in this phase; a clean -race run under load is the goal. Overhead is ~5–10×, so it's a test/CI tool, not a prod one.

Two ways to be safe: share-by-communicating vs mutexes

◆ channels (Go's motto)

"Don't communicate by sharing memory; share memory by communicating." One goroutine owns the state; others send it messages over channels. No locks, no races by construction. This is the hub pattern.

◆ mutexes (sync.Mutex/RWMutex)

A lock guards shared state; hold it for the critical section only. Simpler and faster for plain shared caches/counters. RWMutex allows many readers or one writer. Use when the state is "a thing several goroutines read/update," not "a stream of events."

How to choose (say this in interviews): use channels to transfer ownership / coordinate a pipeline of events; use a mutex to protect a simple shared data structure. Don't force everything into channels — a rate-limit counter is a mutex+map (or Redis), not a goroutine.

The Hub pattern — the heart of presence

The hub is a single goroutine that owns the set of connected clients. All mutations (register, unregister, broadcast) arrive as messages on channels; because only the hub goroutine ever touches the clients map, no mutex is needed and no race is possible. Each client has two goroutines: a readPump (WebSocket → hub) and a writePump (client's send channel → WebSocket).

WebSockets — what the upgrade actually is

A WebSocket starts as an HTTP/1.1 GET with Upgrade: websocket + a Sec-WebSocket-Key. The server replies 101 Switching Protocols with the hashed accept key, and from then on the same TCP connection carries bidirectional, framed messages — no more HTTP request/response. It's full-duplex: server can push anytime. Frames have opcodes (text/binary/close/ping/pong).

  • Ping/pong keepalive: the server periodically pings; if a client doesn't pong within a deadline, the connection is dead — close it and unregister. This is how you detect half-open connections (client vanished without a TCP FIN).
  • One writer rule: a WebSocket connection must be written by exactly one goroutine — that's why writePump is the sole writer, draining the client's send channel. Multiple writers = corrupted frames.
  • Library: github.com/coder/websocket (formerly nhooyr) or gorilla/websocket. Concept is identical.

Redis pub/sub — crossing the instance boundary

The hub only knows clients connected to this process. With multiple presence instances (behind a load balancer), userA on instance-1 and userB on instance-2 can't see each other's messages through in-memory hubs alone. Redis pub/sub is the fan-out bus: when the hub wants to broadcast to a room, it PUBLISHes to a channel room:{id}; every instance SUBSCRIBEs and re-broadcasts to its local clients. Now it scales horizontally.

⚙ under the hood — pub/sub vs Streams, and the fire-and-forget caveat

Redis pub/sub is at-most-once and non-durable: a message published while a subscriber is momentarily disconnected is gone — there's no backlog. That's acceptable for presence/live delivery (a missed "typing…" doesn't matter; the durable message is already in Postgres via Kafka). If you needed replay/durability you'd use Redis Streams or Kafka. Knowing why pub/sub is fine here (ephemeral, best-effort, backed by a durable store elsewhere) is the senior distinction.

Context — cancellation & deadlines as a first-class value

context.Context propagates cancellation down a call tree. ctx, cancel := context.WithCancel(parent) (or WithTimeout/WithDeadline) returns a child; calling cancel() (or the deadline passing) closes ctx.Done(), which every downstream goroutine selects on to stop. Cancellation flows one way: parent cancels children, never the reverse.

  • Always call cancel (usually defer cancel()) even on success — it releases resources; not calling it leaks.
  • Context is for control, not config. Use context.Value only for request-scoped cross-cutting data (trace span, request id), never to pass optional function args.
  • Never store a Context in a struct; pass it as the first parameter down the chain.

Graceful shutdown (Kubernetes-shaped)

On SIGTERM (what K8s sends before SIGKILL ~30s later), you must stop accepting new work and let in-flight work finish. For presence: stop accepting new WebSocket upgrades, then let the hub tell each client to drain its send channel and close cleanly, then exit. signal.NotifyContext gives you a context that's cancelled on the signal; everything downstream already selects on ctx.Done(), so shutdown is "just" cancellation flowing through the tree.

Worker pool & backpressure (built here, reused in Phase 5)

A worker pool is a fixed number of goroutines draining a shared job channel. It bounds concurrency (don't spawn a goroutine per event — that's unbounded and will OOM under load) and provides backpressure: when the job channel is full, submitters block, which propagates "slow down" back to the source instead of buffering unboundedly. A semaphore (buffered channel of tokens, or golang.org/x/sync/semaphore) is the other way to cap concurrency.

type Hub struct {
    rooms      map[string]map[*Client]struct{} // roomID -> set of clients
    register   chan *Client
    unregister chan *Client
    broadcast  chan Broadcast
}

type Broadcast struct { RoomID string; Payload []byte }

func New() *Hub {
    return &Hub{
        rooms:      make(map[string]map[*Client]struct{}),
        register:   make(chan *Client),
        unregister: make(chan *Client),
        broadcast:  make(chan Broadcast, 256), // buffered: absorb bursts
    }
}

// Run is the ONLY goroutine that touches h.rooms -> zero locks, zero races.
func (h *Hub) Run(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            h.closeAll()
            return
        case c := <-h.register:
            set := h.rooms[c.roomID]
            if set == nil { set = map[*Client]struct{}{}; h.rooms[c.roomID] = set }
            set[c] = struct{}{}
        case c := <-h.unregister:
            if set := h.rooms[c.roomID]; set != nil {
                if _, ok := set[c]; ok {
                    delete(set, c)
                    close(c.send)            // signal writePump to stop
                    if len(set) == 0 { delete(h.rooms, c.roomID) }
                }
            }
        case b := <-h.broadcast:
            for c := range h.rooms[b.RoomID] {
                select {
                case c.send <- b.Payload:    // fast client
                default:                     // slow client: drop or disconnect
                    delete(h.rooms[b.RoomID], c); close(c.send)
                }
            }
        }
    }
}
Why the default in the broadcast send: if a client's send buffer is full (it's slow / stalled), a blocking send would freeze the entire hub — one bad client stops everyone. The non-blocking send with a default that drops+disconnects the laggard is a deliberate slow-consumer policy. This exact question ("what if one client is slow?") is a favorite.

type Client struct {
    hub    *Hub
    conn   *websocket.Conn
    roomID string
    send   chan []byte   // buffered; hub -> this client
}

// readPump: connection -> hub. Owns reading. On exit, unregisters.
func (c *Client) readPump(ctx context.Context) {
    defer func() { c.hub.unregister <- c }() // ALWAYS cleanup on exit
    for {
        _, data, err := c.conn.Read(ctx)
        if err != nil { return } // client gone / ctx cancelled -> triggers defer
        // (parse client messages: typing indicators, presence pings, etc.)
        _ = data
    }
}

// writePump: this client's send chan -> connection. THE ONLY WRITER.
func (c *Client) writePump(ctx context.Context) {
    ping := time.NewTicker(30 * time.Second); defer ping.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case msg, ok := <-c.send:
            if !ok { // hub closed send -> graceful close frame
                c.conn.Close(websocket.StatusNormalClosure, "bye"); return
            }
            wctx, cancel := context.WithTimeout(ctx, 10*time.Second)
            err := c.conn.Write(wctx, websocket.MessageText, msg); cancel()
            if err != nil { return }
        case <-ping.C:
            if err := c.conn.Ping(ctx); err != nil { return } // dead peer detection
        }
    }
}
The lifecycle contract: when the peer disconnects, Read errors → readPump returns → its defer sends to hub.unregister → hub deletes the client and close(c.send) → writePump sees ok=false and closes the conn. Every goroutine has exactly one owner responsible for its shutdown. No leaks.

    "context"
    "sync"

// Pool runs up to N workers draining a bounded jobs channel.
type Pool struct {
    jobs chan func(context.Context)
    wg   sync.WaitGroup
}

func New(n, buffer int) *Pool {
    if n <= 0 { n = runtime.NumCPU() }
    return &Pool{jobs: make(chan func(context.Context), buffer)}
}

func (p *Pool) Start(ctx context.Context) {
    for i := 0; i < cap(p.jobs); i++ { /* or n */ }
    for i := 0; i < numWorkers; i++ {
        p.wg.Add(1)
        go func() {
            defer p.wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case job, ok := <-p.jobs:
                    if !ok { return }
                    job(ctx)
                }
            }
        }()
    }
}

// Submit blocks when the buffer is full -> BACKPRESSURE (the caller slows down).
func (p *Pool) Submit(ctx context.Context, job func(context.Context)) error {
    select {
    case p.jobs <- job:
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
}

// Stop: close jobs, wait for in-flight to finish.
func (p *Pool) Stop() { close(p.jobs); p.wg.Wait() }
Two shutdown signals, on purpose: ctx.Done() = "abort now" (drop remaining jobs); close(jobs) + wg.Wait() = "finish queued work then stop" (drain). Which you use depends on whether pending jobs must complete.

Interview drills

Explain the Go scheduler. Why can one server hold 100k idle connections?
Go uses M:N scheduling with the GMP model: goroutines (G) are multiplexed onto OS threads (M) via logical processors (P, count = GOMAXPROCS). Each P has a local run-queue and work-steals when empty. Goroutines start with ~2KB growable stacks and context-switch in userspace (cheap). Crucially, network I/O uses the netpoller (epoll/kqueue): a goroutine blocked on a socket read is parked and its thread is freed to run others. So 100k idle WebSocket connections are 100k parked goroutines costing a few KB each — not 100k threads. Since 1.14 the scheduler is async-preemptible so CPU-bound goroutines can't starve the rest.
Channels vs mutexes — how do you decide?
Channels to transfer ownership or coordinate a flow of events between goroutines ("share memory by communicating"); a mutex to protect a simple shared data structure that multiple goroutines read/update. The hub uses channels because it's an event flow with a single owner of the map — no lock needed. A rate-limit counter or in-memory cache is better as a mutex+map (or Redis). Forcing everything into channels adds latency and complexity; forcing everything into locks invites deadlocks and contention. Pick per problem.
In your hub, what happens if one client is slow? How do you prevent it from blocking everyone?
Each client has a buffered send channel and a dedicated writePump. When the hub broadcasts, it does a non-blocking send (select with default): if the client's buffer is full it means that client can't keep up, so the hub drops it (deletes from the room and closes its send channel) rather than blocking. Because only the hub goroutine mutates the map, this is race-free. A blocking send would let one stalled client freeze the entire hub — the classic head-of-line problem — which the slow-consumer policy prevents.
What's a goroutine leak and how do you avoid it here?
A goroutine that never terminates (blocked forever on a channel/IO with no cancellation path), accumulating until you OOM. Avoided by: every long-lived goroutine selects on ctx.Done(); every connection's goroutines have a single owner that closes them (readPump's defer unregisters; hub closes send; writePump exits on closed send or ctx). Verify with pprof — goroutine count should return to baseline after clients disconnect. Never start a goroutine without knowing exactly how it stops.
Why is Redis pub/sub acceptable for live delivery but not for the messages themselves?
Redis pub/sub is at-most-once and non-durable — no backlog, so anything published while a subscriber is briefly disconnected is lost. That's fine for ephemeral live fan-out (presence, typing, real-time push) because the durable copy of the message already exists in Postgres (written before the Kafka event). If a live push is missed, the client re-fetches history and is consistent. For anything that must not be lost you use Kafka or Redis Streams, which retain and replay.
How does graceful shutdown work end-to-end?
signal.NotifyContext yields a context cancelled on SIGTERM. The HTTP/WS server stops accepting new upgrades via Shutdown. Because every long-lived goroutine (hub, redis subscriber, client pumps, worker pool) already selects on ctx.Done(), cancelling the root context unwinds the whole tree: the hub closes each client's send channel, writePumps send WebSocket close frames and exit, pumps' defers unregister. In Kubernetes this matters because pods get SIGTERM then ~30s then SIGKILL — draining in that window avoids dropping live connections and in-flight work.

Theory — consuming reliably

Offset management = your delivery guarantee

Recall from Phase 3: the group's committed offset records "processed up to here." kafka-go in group mode auto-commits by default, which quietly gives you at-most-once-ish semantics (offset can advance before your work succeeds). To get real at-least-once you disable auto-commit and commit manually after successful processing with reader.CommitMessages(ctx, msg). Crash before commit ⇒ reprocess on restart. No loss.

at-least-once loop: msg = FetchMessage(ctx) // read WITHOUT committing err = process(msg) if err == nil: CommitMessages(ctx, msg) // advance offset ONLY on success else: retry / dead-letter, then commit to move on

Idempotency — because duplicates will happen

At-least-once means the same message.sent can arrive twice (crash between process and commit, or a rebalance replays). A push sent twice is a bug. Idempotency makes reprocessing harmless. Two mechanisms:

dedupe by event id

Track processed EventIDs (a Redis SET key NX EX or a processed_events table). If already seen, skip. The NX ("set if not exists") makes the check-and-mark atomic.

idempotent effect

Design the side effect to be naturally repeatable: upsert instead of insert, "ensure notification exists" instead of "create." Best when feasible — no extra state.

Provider idempotency keys: real push/email providers (FCM, SendGrid, Stripe) accept an idempotency key — pass your EventID and the provider dedupes for you. Mention this; it's the production-grade answer.

Retry, backoff, and jitter

Transient failures (provider 503, network blip) should be retried; permanent ones (malformed payload) should not. Retry with exponential backoff: wait base × 2^attempt between tries (1s, 2s, 4s…), capped at a max. Add jitter (randomize the delay) so a thousand consumers that failed at the same instant don't all retry at the same instant — the thundering herd that turns a blip into an outage.

⚙ under the hood — retry where? in-process vs retry topics

In-process retry (sleep+loop) is simplest but blocks that partition — you can't advance past a stuck message without either succeeding or giving up. For long/철 retries, the scalable pattern is tiered retry topics (notif.retry.5s, notif.retry.1m…): on failure, republish to a delay topic and commit the original, so the main partition keeps flowing. For this roadmap, do bounded in-process retry (e.g. 3 attempts) then dead-letter — and know the retry-topic pattern for the interview.

Dead-letter queue (DLQ) — for poison messages

A poison message fails every time (bad schema, references a deleted user). Retrying forever blocks the partition and wastes resources. After max retries, publish it to a dead-letter topic (notification.dlq) with metadata (original topic, error, attempt count, timestamp), then commit the original offset so the consumer moves on. The DLQ is inspected/alerted/replayed by ops — failures become visible and recoverable instead of silently blocking or being lost.

Backpressure — the correct response to overload

If notifications dispatch slower than events arrive, you must not keep reading unboundedly (OOM) or drop messages (data loss). The right answer: stop reading. Feed fetched messages into the bounded worker-pool channel from Phase 4; when it's full, Submit blocks, which stops the fetch loop, which stops polling Kafka. Kafka happily retains the backlog (that's its whole point) and the consumer catches up when it can. Consumer lag (how far behind the latest offset) rises temporarily — a metric to watch, not a crash.

Say this exactly: "Under overload I apply backpressure — block the consumer instead of buffering or dropping. Kafka is the buffer; lag is the signal. Then I scale consumers (up to partition count) or add partitions." That's the senior answer to "what happens when notification can't keep up?"

        msg, err := n.consumer.Fetch(ctx)
        if err != nil {
            if errors.Is(err, context.Canceled) { return nil } // graceful stop
            n.log.Error("fetch failed", zap.Error(err)); continue

        m := msg
        if err := n.pool.Submit(ctx, func(ctx context.Context) {

            _ = n.consumer.Commit(ctx, m) // commit AFTER processing (incl. dead-letter)
        }); err != nil {

        }
    }

func (n *Notifier) handle(ctx context.Context, m kafkago.Message) {
    var e events.MessageSent
    if err := json.Unmarshal(m.Value, &e); err != nil {
        n.deadLetter(ctx, m, "unmarshal", err); return // poison -> DLQ immediately
    }
    // SET dedupe:{EventID} 1 NX EX 86400  -> true only the FIRST time
    ok, _ := n.rdb.SetNX(ctx, "dedupe:"+e.EventID, "1", 24*time.Hour).Result()
    if !ok {
        n.log.Info("duplicate event skipped", obs.TraceFields(ctx, zap.String("event_id", e.EventID))...)
        return // already processed -> idempotent no-op
    }
    if err := n.dispatchWithRetry(ctx, e); err != nil {
        n.rdb.Del(ctx, "dedupe:"+e.EventID) // allow reprocessing since we DID NOT succeed
        n.deadLetter(ctx, m, "dispatch", err)
    }
}
Subtle but important: if dispatch ultimately fails and you dead-letter, delete the dedupe key so a future replay can retry — otherwise a transient failure becomes permanent. Idempotency keys should mark success, not merely attempt (or use a two-state: pending→done).

Retry with exponential backoff + jitter
Bounded attempts; retry transient, fail-fast permanent.
▶
go dispatchWithRetry
func (n *Notifier) dispatchWithRetry(ctx context.Context, e events.MessageSent) error {
    const maxAttempts = 3
    base := 500 * time.Millisecond
    var err error
    for attempt := 0; attempt < maxAttempts; attempt++ {
        err = n.provider.Push(ctx, e) // the actual side-effect (FCM/APNs/etc.)
        if err == nil {
            return nil
        }
        if !isTransient(err) {
            return err // permanent -> don't waste retries, go straight to DLQ
        }
        // exponential backoff with full jitter
        backoff := base * time.Duration(1<<attempt)      // 500ms, 1s, 2s
        sleep := time.Duration(rand.Int63n(int64(backoff))) // full jitter
        select {
        case <-time.After(sleep):
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return fmt.Errorf("dispatch exhausted after %d attempts: %w", maxAttempts, err)
}
Full jitter (rand(0, backoff)) is AWS's recommended variant — it spreads retries widest and minimizes collision. Always select on ctx.Done() during the sleep so shutdown isn't delayed by a pending backoff.

func (n *Notifier) deadLetter(ctx context.Context, m kafkago.Message, stage string, cause error) {

}

Phase 5 exit criteria

  • At-least-once: offsets committed only after processing/dead-lettering; crash mid-process reprocesses
  • Idempotent: duplicate EventIDs are skipped; a re-delivered event never double-notifies
  • Bounded retry with exponential backoff + jitter; permanent errors fail fast
  • Poison messages land in the DLQ with metadata + trace; a replay path exists
  • Overload applies backpressure (block, not buffer/drop); lag + queue depth are metrics

Interview drills

How do you make a Kafka consumer at-least-once instead of at-most-once?
Disable auto-commit and commit the offset only after the message is successfully processed (or dead-lettered). Read with FetchMessage, process, then CommitMessages. If the consumer crashes after processing but before committing, the message is redelivered on restart — no loss, but possible duplicates, which is why consumers must be idempotent. Auto-commit advances the offset on a timer regardless of your work's success, which risks skipping unprocessed messages (at-most-once).
Duplicates are guaranteed with at-least-once. How do you prevent double notifications?
Idempotency keyed on a stable event id. Before dispatching, atomically mark the event as being processed — e.g. Redis SET dedupe:{eventID} NX EX; if the key already existed, skip. Or make the effect naturally idempotent (upsert), or pass the event id as the provider's idempotency key so the provider dedupes. Mark success, not just attempt, so a failed dispatch can still be retried/replayed.
Why exponential backoff with jitter, not fixed-interval retry?
Fixed intervals retry a struggling dependency too aggressively and, worse, synchronize many clients that failed together into simultaneous retry waves — a thundering herd that keeps the dependency down. Exponential backoff (doubling delays, capped) reduces pressure over time; jitter randomizes the timing so retries spread out instead of colliding. Full jitter (random between 0 and the backoff) spreads widest.
What is a poison message and what do you do with it?
A message that fails every time — malformed payload, references deleted data, a permanent downstream rejection. Retrying it forever blocks the partition (you can't advance the offset) and burns resources. After bounded retries you route it to a dead-letter topic with metadata (original topic/partition/offset, error, attempt count, trace headers) and commit the original offset so the consumer proceeds. Ops alerts on the DLQ, fixes the root cause, and replays.
Notification can't keep up with the incoming rate. What happens?
Apply backpressure: stop consuming rather than buffering unboundedly (OOM) or dropping (data loss). Fetched messages feed a bounded worker-pool channel; when it's full, submit blocks, the fetch loop stalls, and polling stops. Kafka is the durable buffer — it retains the backlog — and consumer lag rises as the signal. Then I scale horizontally by adding consumers up to the partition count, or add partitions for more parallelism. The point: the system degrades in latency, not correctness.
You process messages concurrently in a worker pool. What's the offset-commit hazard?
Committing an offset commits everything up to it. If workers finish out of order and each commits its own message, you can commit a higher offset while a lower one is still in flight — a crash then skips the unfinished lower message (silent loss). Fixes: commit only the highest contiguous completed offset, or process in batches and commit the batch boundary, or partition work by key so a single worker owns ordering. Concurrency for throughput, ordered commits for correctness.

Theory — the three pillars & how they connect

traces

Causal, per-request. "Where did this one request spend its time / fail?" A tree of spans across services. Best for latency & dependency debugging.

metrics

Aggregated, numeric, cheap. "How is the system doing overall?" Rates, error %, latency percentiles. Best for dashboards & alerts.

logs

Discrete events with detail. "What exactly happened at this moment?" Best for forensic detail. Correlated to traces via trace_id.

◆ the workflow that ties them together

A metric/alert says "error rate up in messaging." You pull the RED dashboard, see p99 latency spiking. You click into an exemplar trace and see the DB span is slow. You take that trace's trace_id, search Kibana, and read every log line from every service for that exact request. Metrics find it, traces localize it, logs explain it. This loop only works if all three share the trace id.

OpenTelemetry, the full picture (SDK → Collector → backend)

Phase 1 gave you the SDK basics (provider, span, exporter, propagator). Production adds the OTel Collector: your services export OTLP to a local collector, which batches, processes (sampling, redaction, enrichment), and fans out to backends (Tempo/Jaeger for traces, Prometheus for metrics, Loki/ELK for logs). Decoupling apps from backends via the collector means you change vendors without touching app code.

⚙ under the hood — how a trace crosses gRPC and Kafka

Across gRPC: the otelgrpc client interceptor injects the traceparent into request metadata; the server interceptor extracts it and starts a child span. You get cross-service traces by adding two interceptors — no manual work per call.

Across Kafka is manual and worth knowing: the producer injects the span context into the Kafka message headers (via the propagator); the consumer extracts them and starts a span whose parent is the producer's span. This is how a trace survives an asynchronous hop — the DB write in messaging, the Kafka produce, and the notification dispatch minutes later all appear in one trace (linked as producer→consumer).

Prometheus — pull model & the four metric types

Prometheus scrapes a /metrics HTTP endpoint on each service every N seconds (pull, not push) and stores time series labeled by dimensions. Pull means Prometheus controls load and can tell "target down" from "no data." Four metric types:

TypeSemanticsExample here
CounterMonotonic ↑ (reset on restart). Query with rate().messages_sent_total, notifications_dead_lettered_total
GaugeGoes up/down; a current value.worker_pool_queue_depth, ws_connections, consumer_lag

⚙ under the hood — why histograms, and the average trap

Never alert on averages. An average latency of 50ms can hide that 1% of requests take 5s — and those are your angriest users. Histograms bucket observations so you can compute p95/p99 with histogram_quantile(0.99, rate(..._bucket[5m])), and because buckets are counters they aggregate correctly across instances (summaries don't). Watch tail latency, not the mean. Beware high-cardinality labels (user_id!) — each label combination is a separate time series and will blow up memory.

Grafana — RED & USE, the two dashboard recipes

RED (per service / request-driven)

Rate (req/s), Errors (fail %), Duration (p50/p95/p99). Answers "is this service healthy?" in three numbers. Build this first, per service.

USE (per resource)

Utilization, Saturation, Errors — for CPU, memory, pool, disk. Answers "is this resource the bottleneck?" e.g. pg pool saturation, Kafka consumer lag, Redis memory.

ELK & structured log correlation

zap emits JSON logs (Phase 1). A shipper (Filebeat/Fluent Bit) tails container stdout and ships to Elasticsearch; Kibana queries/visualizes. The one field that makes this powerful is trace_id (you already add it via obs.TraceFields) — Kibana search trace_id:"abc123" returns the full cross-service story of one request.

Health checks — liveness vs readiness (not the same thing)

/healthz — liveness

"Is the process alive/not deadlocked?" Cheap, no dependencies. If it fails, the orchestrator restarts the pod. Must NOT check the DB — a DB blip shouldn't trigger mass restarts.

/readyz — readiness

"Can it serve traffic right now?" Checks dependencies (DB ping, Redis ping, Kafka). If it fails, the orchestrator stops routing traffic (removes from load balancer) but doesn't restart. Self-heals when deps recover.

The classic mistake: putting DB checks in liveness. A transient DB outage then makes every pod fail liveness and restart-loop simultaneously, turning a small blip into a full outage. Dependencies belong in readiness.

Profiling (pprof) & load testing

net/http/pprof exposes live profiles at /debug/pprof/: goroutine (leak hunting), heap (allocations/leaks), profile (30s CPU), block/mutex (contention). Under a k6/hey load test you drive realistic traffic, watch the RED dashboard for saturation, and use pprof to find the hot function or the leaking goroutine. This is how you turn "it's slow" into "SendMessage spends 60% of CPU in JSON marshalling" — the difference between guessing and knowing.

Interview drills

Traces, metrics, logs — when do you reach for each?
Metrics for aggregate health and alerting — cheap, numeric, always-on (rate/errors/latency percentiles). Traces for per-request causal debugging — where in the call graph did time go or a failure occur. Logs for forensic detail — what exactly happened at a moment. The workflow: a metric alert fires → RED dashboard shows a spiking p99 → open an exemplar trace to localize the slow span → take its trace_id to Kibana to read the detailed logs. They're complementary and joined by the trace id.
How does a single trace survive an asynchronous Kafka hop?
Via context propagation into message headers. The producer starts a span and uses the OTel propagator to inject the span context (W3C traceparent) into the Kafka record's headers. The consumer extracts those headers back into a context and starts its span as a child (or a link) of the producer's. So even though the consume happens seconds later in a different process, it's stitched into the same trace — you can literally see the time the message spent waiting in the topic. gRPC does the same automatically via interceptors; Kafka you wire manually.
Why never alert on average latency?
Averages hide the tail. A 50ms mean can mask that 1% of requests take 5s — precisely the users who are furious. You alert on percentiles (p95/p99) computed from histogram buckets. Histograms also aggregate correctly across instances (Prometheus summaries compute quantiles client-side and can't be merged). So: histogram metrics, histogram_quantile for p99, alert on the tail and on error rate, not the average.
Liveness vs readiness — and the classic mistake?
Liveness answers "is the process wedged?" — cheap, no dependencies; failure triggers a restart. Readiness answers "can I serve traffic now?" — checks DB/Redis/Kafka; failure removes the pod from the load balancer without restarting. The classic mistake is checking the DB in liveness: a transient DB outage then fails liveness on every pod at once, triggering a synchronized restart storm that amplifies a small blip into a full outage. Dependencies belong in readiness, which self-heals when they recover.
Prometheus is pull-based. Why is that good, and what's the cardinality trap?
Pull means Prometheus scrapes targets on its own schedule, so it controls load, can distinguish "target down" from "no data," and needs no push credentials in every app. The cardinality trap: each unique combination of label values is a separate time series. Labeling by unbounded values (user_id, message_id, full URLs) explodes series count and OOMs Prometheus. Keep labels low-cardinality and bounded (method, status code, service); put high-cardinality identifiers in traces/logs, not metric labels.
The system is "slow." Walk me through diagnosing it.
Start at metrics: RED dashboard tells me which service and whether it's latency or errors. USE panels tell me if a resource is saturated (pg pool at max, consumer lag climbing, CPU pegged). I open an exemplar trace to see which span dominates — say the DB span. I confirm with the DB duration histogram and an EXPLAIN (missing index?). If it's CPU, I take a 30s pprof profile and read the flame graph for the hot function; if memory/goroutines climb, a heap/goroutine profile finds the leak. Then I fix the specific thing, re-run the k6 load test, and prove the before/after on the dashboard. Evidence at every step — never guess.

    t.Run(tt.name, func(t *testing.T) {

    select {
    case <-ctx.Done(): return

    }
